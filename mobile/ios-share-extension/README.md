# iOS Share Extension — Setup

Like `mobile/android-overlay/`, this is a **source drop**, not a standalone buildable
Xcode project. Xcode project files (`.pbxproj`) are binary-adjacent, tool-generated, and
not something to hand-author reliably — the standard, correct way to add a Share
Extension is Xcode's own target wizard, which wires up the `.pbxproj`, code signing, and
embed-extension build phase correctly. This sandbox has no macOS/Xcode, so **none of this
has been compiled or run** — it's been written carefully against current, public iOS APIs
(`UniformTypeIdentifiers`, `URLSession`, standard `NSExtension` share-sheet contract), but
build and test it in Xcode before shipping.

## What's here

```
ios-share-extension/
  EquiEdgeShare/
    Info.plist                — NSExtension contract: image-only activation rule
    ShareViewController.swift — the extension's UI + image extraction (no storyboard)
    AnalyzeAPI.swift           — POST /mobile/analyze networking, shared with any future
                                 App Intent (see ../ios-screen-capture-research.md)
```

## Setup steps (in Xcode, on macOS)

1. Open the RN app's `.xcworkspace` (generated by `react-native init` / `pod install`
   from `mobile/`).
2. **File → New → Target… → Share Extension.** Name it `EquiEdgeShare`. Xcode generates a
   stub `ShareViewController.swift`, `Info.plist`, and (if you don't uncheck it) a
   storyboard.
3. Delete the generated storyboard file entirely (this extension builds its UI in code —
   see `NSExtensionPrincipalClass` in the provided `Info.plist`, which deliberately omits
   `NSExtensionMainStoryboard`).
4. Replace the generated `ShareViewController.swift` and `Info.plist` with the files in
   this folder, and add `AnalyzeAPI.swift` to the extension target's file list too (Xcode's
   wizard won't generate it — it's new).
5. Set the extension target's **Deployment Target to iOS 14.0+** —
   `UniformTypeIdentifiers.UTType` (used to detect the shared image) requires iOS 14; this
   is a deliberate floor, not an oversight (iOS 14 shipped in 2020; there is no reason to
   support older versions for a 2026 app).
6. Set the extension's **Bundle Identifier** to `<main app bundle id>.share`
   (e.g. if the main app is `ai.equiedge.mobile`, the extension must be
   `ai.equiedge.mobile.share`) — Apple requires an extension's bundle ID to be prefixed by
   its containing app's bundle ID.
7. Build & run the main app target once to embed the extension; the share sheet entry
   ("EquiEdgeAI") should then appear when sharing a screenshot from Photos.

## Runtime flow

```
User takes a screenshot of ClubGG (iOS Screenshot: side button + volume up)
  -> taps the screenshot thumbnail -> Share
  -> "EquiEdgeAI" appears in the share sheet (image-only activation rule)
  -> tap it -> extension opens, image loads automatically (no extra tap needed)
  -> uploads to POST /mobile/analyze
  -> shows winrate + action -> tap Done -> back to whatever app you were in
```

That's the whole interaction: screenshot → Share → EquiEdgeAI → result → Done.

## Why `SLComposeServiceViewController` was NOT used

Apple's `SLComposeServiceViewController` is the base class most share-extension tutorials
reach for — it's built for composing a caption/post (think: "share to Twitter"), with a
text field and a "Post" button. That UI has no purpose here and would add an unnecessary
screen/tap between "user shares a screenshot" and "user sees a decision." A plain
`UIViewController` with a tiny hand-built layout is the leaner, correct choice for this
specific product shape.

## Known limitations / follow-ups

- **Not verified by an actual Xcode build** — no macOS in this environment. Build it and
  fix whatever the compiler/linker flags before shipping.
- **HEIC images are not supported.** A real screenshot (side button + volume up) is always
  PNG, which is the documented, intended input — but if a user instead shares an ordinary
  camera-roll *photo*, it may be HEIC, and the backend's Pillow-based decoder does not
  read HEIC without an additional plugin. The extension will surface the backend's
  generic "couldn't read the image" error in that case rather than crash, but a clearer
  "screenshots only" message could be added client-side later if this proves confusing.
- **No retry-with-backoff** — a failed upload just shows the error + Done; the user
  re-shares to retry. Given this is a single lightweight request, that's an acceptable
  MVP tradeoff rather than a gap that needs its own retry queue.
- **App icon / privacy manifest**: newer Xcode versions auto-generate a
  `PrivacyInfo.xcprivacy` for new targets — accept that default; this extension makes one
  network call and touches no privacy-sensitive APIs (contacts, location, etc.) beyond the
  photo the user explicitly shared.
